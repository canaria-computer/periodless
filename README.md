### 主役は複式簿記そのもの

プロジェクトの中心にあるのは、一般的なCRUDアプリケーションではなく、複式簿記そのものです。

会計上の概念と不変条件を、永続化層やUIの都合で隠さないことを重視します。

特に、次を基本原則とします。

- 仕訳は会計上の事実を記録する。
- 借方と貸方は常に均衡する。
- 総勘定元帳、試算表、財務諸表は仕訳から導出される。
- 会計上のルールは永続化アダプタやUIではなく、ドメインコアに属する。

### 一度記録した会計上の事実は不変

既存の会計上の事実を上書きしたり、物理的に削除したりしません。

訂正は、元の事実を取り消す・修正する・置き換える新しい事実を追加することで表現します。考え方としては、可変な
`UPDATE` よりも Git の `revert` に近いものです。

```text
元の仕訳
    |
    +--> 取消・訂正
              |
              +--> 正しい仕訳
```

これにより、履歴を常に確認・監査できます。

### 永続化はドメインではなくアダプタの責任

会計コアは、特定のDBやストレージ方式に依存してはいけません。

永続化は、小さなインターフェース（port /
trait）を通じて外部から提供されます。アダプタは、次を担当します。

- シリアライズとパース
- DB固有のクエリ
- 保存の仕組み
- 必要なトランザクション処理
- ストレージ表現とドメインオブジェクトの変換

アダプタは会計ルールを持ちません。

コアは、PostgreSQL、MySQL、SQLite、ファイル、メモリなど、どこに保存されているかを知りません。

実用上の主な永続化先としては、整合性制約、トランザクション、各種制約などを備えるRDBMSを想定します。ただし、それは実装上の選択であり、ドメイン上の前提ではありません。

### インターフェースは可能な限り小さく

インターフェースには、コアが本当に必要とする能力だけを公開します。

基盤がRDBMSだからといって、巨大なCRUDインターフェースを作ることは避けます。

追加専用の仕訳履歴であれば、任意の `update` / `delete` よりも `append` / `read`
/ `scan` のような能力を優先します。

```text
Core
  |
  | 小さな port / trait
  v
Adapter
  |
  +--> PostgreSQL
  +--> MySQL
  +--> SQLite
  +--> ファイル / メモリ / その他
```

ストレージの実装を差し替えても、会計ロジックを変更せずに済むことを目標とします。

## 時間軸と追加専用モデル

このプロジェクトは、時間と不変な履歴を中心に設計します。

必要性が明確な場合には、6NF的な時間軸分解を含む高度な正規化を採用します。目的は正規化そのものではなく、既存の事実を上書きせず、過去の状態を保存し、現在の状態を履歴から導出できるようにすることです。

重要なのは次の区別です。

> **現在の状態は、権威あるデータそのものではなく、過去の事実から導出されるビューである。**

```text
不変な事実
    |
    v
  計算
    |
    +--> 現在の仕訳ビュー
    +--> 総勘定元帳
    +--> 試算表
    +--> 損益計算書
    +--> 貸借対照表
```

会計上の真実を可変なコピーとして保持するより、権威ある仕訳・履歴から現在値を導出することを優先します。

## ハッシュチェーン

仕訳・履歴のレコードをハッシュで連結し、過去のレコードが改変・除去されたことを検出できるようにする場合があります。

単純化すると次のような構造です。

```text
entry 1 --hash--> H1
                    |
entry 2 --hash--> H2
                    |
entry 3 --hash--> H3
```

ハッシュチェーンは履歴の完全性を確認するための仕組みであり、会計ルールそのものではありません。また、ブロックチェーンを実装することを目的としません。

## キャッシュとValkey

長い履歴から毎回すべてを再計算するとコストが高くなる場合があります。

そのため、Valkeyを派生結果や中間計算のキャッシュとして利用できます。

不変な履歴のハッシュは、その履歴に基づく計算結果のキャッシュ識別子として利用できます。

```text
履歴ハッシュ H5
    |
    +--> TrialBalance(H5) -> キャッシュ

仕訳6を追加
    |
    v
履歴ハッシュ H6
    |
    +--> 必要に応じて H5 + 仕訳6 から導出
```

キャッシュは真実の源泉ではありません。キャッシュを失っても、会計データと正しさを失わず、再構築できなければなりません。

## プロジェクトの境界

## Agentic TDD と実行可能な知識

開発には **Agentic Test-Driven Development（Agentic TDD）**
を基本的な開発パラダイムとして採用します。

**Test-Driven Generation（TDG）** や **Test-Driven Prompt Engineering（TDPE）**
という関連用語は、同じ実践の特定の側面を表すときに利用できます。本プロジェクトでは、これらを別々の方法論として形式化するのではなく、`Agentic TDD`
を包括的な呼称として扱います。

目指すのは「LLMにコードを書かせ、結果を人間が眺める」開発ではありません。リポジトリ自身が、AI
Agentが繰り返し検証できる実行可能な目標を提供します。

```text
要求
  ↓
OpenSpec / 合意済み設計
  ↓
失敗するテスト
  ↓
最小限の実装
  ↓
テスト成功
  ↓
リファクタリング
  ↓
rustdoc / doctest / 回帰テスト
```

これらの実践について、プロジェクト独自の用語を無闇に作らず、既存の業界用語を積極的に借用します。異なるAI
Agentやモデルを使い分けても、同じ前提を短く共有できるためです。

ただし、手順を儀式化することは目的ではありません。ドメインの振る舞いや不変条件にはTDDを強く適用しつつ、軽微な変更まで過剰な手順にして開発が止まらないようにします。

## LLMを使った開発の原則

このプロジェクトはLLMによる開発支援を前提としています。以下はプロジェクトの開発原則です。

### 可変なCRUD意味論を勝手に導入しない

既存の会計記録を上書きすることで訂正する実装を、単純だからという理由だけで導入しません。

会計上の事実について、明示的な理由なく `UPDATE` / `DELETE`
の意味論をドメインに持ち込まないでください。

### ドメインルールをアダプタへ移さない

アダプタは、仕訳が正しいか、借方・貸方が残高へどう影響するか、訂正が会計上何を意味するかを決めません。

それらはドメインコアの責任です。

### コアを特定のDBへ結びつけない

利便性のために、会計コアへDBドライバを直接導入しません。

PostgreSQL、MySQL、SQLite固有の動作をドメインロジックの前提にしません。

### 重複した状態より導出を優先する

計算によって求められる値を保存フィールドとして追加する前に、その値を権威ある履歴から導出できないか検討します。

キャッシュやマテリアライズされた値は、派生データとして明示的に扱い、再生成できることを前提にします。

### 最小の抽象化を優先する

抽象化できるからという理由だけで抽象化を追加しません。

interface、trait、module、crateは、意味のある境界を作るか、有用な不変条件を強制するときに存在すべきです。

### 会計上の概念を明示する

会計上の意味を消してしまう汎用的な名前より、適切なドメイン用語を優先します。

コードを見れば、それが複式簿記のどの概念を表しているか分かることを目指します。

### 便利さより正しさを優先する

少し実装が面倒になっても、監査可能性、不変性、会計上の正しさを維持できるなら意味論的に正しいモデルを選びます。

## 非目標

このプロジェクトは、当面次を目指しません。

- 完全なERP
- 税務申告プラットフォーム
- 給与計算システム
- ブロックチェーン
- 分散データベース
- 汎用ORMやDB抽象化層
- 専門家向け会計ソフトの置き換え

初期スコープは意図的に小さく、複式簿記を理解し、正しく実装することです。

## 開発方針

最小限の有用なクレートから始め、あらかじめ大きなアプリケーションフレームワークを設計するのではなく、会計モデルから徐々に成長させます。
