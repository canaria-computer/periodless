# Design

## Context

動機は proposal.md の「Why」、追加要件は
`specs/journal-entry-dsl/spec.md`、既存の構文要件は
`openspec/specs/journal-entry-dsl/spec.md` を参照する。

既存の `crates/periodless-journal-dsl` は pest
による構文解析のみを提供し、解析結果（`JournalEntryDescription` /
`DescribedDetail`）は科目名と元の金額表現を `String`
で保持する。`crates/periodless-core` はまだドメイン型を持たない。

## Goals / Non-Goals

**Goals:**

- 整形出力を「再解析可能で冪等」な正規形として定義し、テストで固定する。
- 整数変換を DSL
  クレート内で完結させ、通貨モデル（最小通貨単位）の決定を本変更に引き込まない。
- 表示幅の算出を外部クレートに委ね、桁揃えのロジックを単純に保つ。

**Non-Goals:**

- 整形幅・区切り記号・インデントの設定可能化（要求が出た時点で追加する）。
- 単位を持つ金額 Newtype（`Amount`）の導入と、`periodless-core` への変更。
- 解析結果から `JournalEntry` を構築する意味検証。

## Decisions

### 1. 整数変換は DSL クレート内で完結させ、`i64` を返す

`DescribedDetail::amount_as_integer(&self) -> Result<i64, AmountOverflow>`
を追加する。既存の `amount_expression() -> &str` は変更しない。

- **`periodless-core` に単位付きの金額型を置かない**:
  ドメイン金額型は「最小通貨単位が円か銭か」という通貨モデルの決定を伴う。本変更に必要なのは「金額表現が表す整数」だけであり、単位の決定を先取りすると誤った前提を固定してしまう。したがって
  core には触れず、DSL クレートは `periodless-core` に依存しない。
- **`i64` を選ぶ理由**: 非負の `i64` 同士の減算は必ず `i64`
  に収まるため、残高・貸借差額・当期純損失といった後段の差額計算が素直になる。`u64`
  では減算ごとに `checked_sub` と符号の持ち回り、あるいは `i128`
  への退避が必要になる。データベースや外部表現（BIGINT）との相互運用も符号付きが素直で、上限
  922 京はドメインに対して十分。
- **生のプリミティブを返すことの位置づけ**: AGENTS.md
  の「金額を生のプリミティブで引き回さない」規則が守るのはドメインコアのAPI境界である。ここは構文層の出力であり、単位を決めずに
  Newtype を作ると上記の前提固定を招くため、意図して `i64` を返す。単位付き
  Newtype への詰め替えは利用側（将来の core アダプタ）の責務とし、rustdoc
  に明記する。
- 変換は ASCII 数字以外を除去した数字列を `str::parse::<i64>()`
  で解釈する。範囲超過は `AmountOverflow`
  として返し、構文解析側は桁数上限を持たない仕様のまま変えない。負の値は、金額表現が
  ASCII 数字で始まり ASCII
  数字で終わる構文上の制約と、符号文字を数字列から除去する変換規則の二重で排除される。

### 2. 整形出力はカンマ挿入を文字列操作で行い、整数変換を経由しない

金額の正規化は「ASCII 数字の抽出 → 先頭ゼロの除去 →
右から三桁ごとのカンマ挿入」の文字列操作で行う。整数へ変換してから書式化すると
`i64`
の範囲に収まらない金額表現を整形できず、整形APIが失敗し得る型になってしまう。文字列操作であれば桁数上限の影響を受けず、整形は常に成功する。

### 3. 表示幅は `unicode-width` に委ねる

`unicode_width::UnicodeWidthStr::width`
で科目名・金額の表示幅を求める。`chars().count()`
では日本語の科目名が等幅フォント上でズレるため採用しない。依存は
`periodless-journal-dsl` のみに追加する（`periodless-core` は依存ゼロを維持）。

### 4. 公開APIの形

- `JournalEntryPrinter::new().print(&description) -> String`
- `impl Display for JournalEntryDescription`（既定の整形設定に委譲）

設定項目を持たない段階でも、将来の整形オプションを `JournalEntryPrinter`
のメソッドチェーンとして追加できる形にしておく。`Display`
を同時に実装するのは、ログや `to_string()` での利用が自然であるため。

### 5. 列の組み立て

借方側・貸方側それぞれについて「科目名の最大表示幅」と「正規化後の金額の最大表示幅」を求め、各行を次の形で組み立てる。

```text
<借方科目名を左詰め> <借方金額を右詰め> / <貸方科目名を左詰め> <貸方金額を右詰め>
```

- 貸方が存在しない行は `/` で終える（スラッシュの後ろに空白を置かない）。
- 借方が存在しない行は借方列の幅ぶんを空白で埋め、スラッシュの位置を揃える。
- 借方が一件も存在しない仕訳では借方列を出力せず、各行を `/` から始める。
- 貸方科目名の左詰めは金額の右揃えのために必要な内部空白であり、行末には現れない。

この組み立てが再解析を壊さない理由:
桁揃えで挿入される空白は「科目名と金額の区切り」および「行頭」にしか現れず、構文は明細前後の水平空白を科目名に含めない。科目名内部の空白はそのまま出力されるため、再解析で元の科目名が復元される。

## Risks / Trade-offs

- 金額を正規化するため `parse → print → parse` で金額表現の文字列は一致しない →
  冪等性（`print(parse(print(x))) == print(x)`）と整数値の一致をテストで固定し、仕様にも明記する。
- 等幅フォント以外では桁揃えが視覚的に揃わない → 表示幅は East Asian Width
  に基づく定義であり、フォント依存の見え方は対象外とする。
- `unicode-width` のバージョン更新で幅の判定が変わり得る →
  期待値を固定した統合テストで検出する。
