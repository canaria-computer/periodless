# Design

## Context

`crates/periodless-core` は現在スタブ関数のみで、`crates/periodless-journal-dsl`
は仕訳テキストの構文解析（`JournalEntryDescription`:
科目名＋金額表現の借方/貸方列、`amount_as_integer() -> Result<i64, AmountOverflow>`）まで実装済み。勘定科目IDのビットレイアウトは
`account-id-encoding` 仕様と `docs/勘定科目一覧/accounts.yaml`
で確定している（`0xC000_LLLL_BBBB_0000`）。本変更はこのコアに最初の実ドメイン実装として仕訳の記録（レコード・ハッシュチェーン・台帳）と仕訳記述の検証を追加する（動機は
`proposal.md` を参照）。合意済みの材質的判断は次のとおり: 勘定科目＝`AccountId`
Newtype / 金額＝**1銭単位**の i64 Newtype / ハッシュ＝BLAKE3 /
日時＝hifitime＋Newtype（正準表現は
`YYYYMMDDTHHMMSS.sssZ`、構築時ミリ秒切り上げ・正規化済み瞬間を保持・年0000〜9999・SS=60許容）/
附随情報＝当面フィールドなし / 台帳＋検証込み /
バリデーション＝違反と警告の7ルール。

## Goals / Non-Goals

**Goals:**

- `periodless-core`
  に、仕訳レコードの構築・検証・ハッシュチェーン・追記専用台帳を、`coding-standards`
  仕様（Newtype・`Result`・パニック禁止・フルーエントAPI・rustdoc/doctest）に従って実装する。
- 1銭単位での金額保持により、割合計算・按分に丸め誤差が発生しないことを保証する。
- 7つの検証ルールを「違反（拒否）」と「警告（受理して通知）」に区分して実装し、検証結果の語彙を単一に保つ。
- 日時正規化（変換例4件・年範囲エラー・冪等性・決定性を含む）とハッシュ preimage
  のバイト構成を一意に定める。

**Non-Goals:**

- DSL→コアの科目解決（科目名から `AccountId` への写像＝科目マスター）は別変更。
- 附随情報の構造、永続化アダプタ、財務諸表ビュー、伝票。
- 現在時刻の取得（システムは時計を持たない）。

## Decisions

### 1. 金額の単位（1銭単位）と `Amount` の設計

- **決定**: `Amount` は**1銭単位（0.01円）の符号付き64bit整数**を保持する
  Newtype とする。公開APIは次のとおり:
  - `Amount::new(sen: i64) -> Result<Amount, AmountError>`:
    1銭単位の値をそのまま構築する（負値は拒否）。
  - `Amount::from_yen(yen: i64) -> Result<Amount, AmountError>`: 円単位から
    checked_mul(100) で構築する（丸めは発生しない）。
  - `Amount::to_yen() -> (i64, i64)`: `(円, 銭)`
    の組を返す（銭未満は存在しないため、円未満の端数を黙って切り捨てない）。
  - 合計は `checked_add` を用い、オーバーフローは `AmountError` として返す。
- **理由**:
  割合計算（百分率・按分）で1円未満の端数が生じても、1銭単位なら整数演算で過不足なく配分できる。浮動小数点を排除し、`i64`
  の範囲（銭単位で約9.2e16円） répondu実務上十分である。
- **代替案**: 円単位の整数（端数を別項目で持つ）、固定小数点、浮動小数点 —
  いずれも端数処理の複雑さが先に立ち、割合計算の目的（丸め誤差の回避）に反する。

### 2. 検証層の配置（どの層でどのルールを判定するか）

- **決定**: 検証は、情報が存在する層で判定する2層構成とする。
  - **`periodless-journal-dsl`（テキスト・行構造・科目名・金額表現）**:
    省略行の位置、科目名末尾が数字の警告、金額表現に関する4ルール（連続する桁区切り文字、桁区切り文字以外の印字可能ASCII文字、基数プレフィックス表記、0埋めされた表記の警告）。行構造（各行の左右の有無）・科目名テキスト・金額表現テキストを保持するのはDSL層のみであり、`JournalEntryDescription`
    に行構造を保持・公開し、DSLクレートに検証器を追加する。構文解析関数自体は検証を行わない（既存「構文解析と意味検証の責任分担」要件を維持）。
  - **`periodless-core`（勘定科目ID・金額）**:
    同一勘定科目の重複、自己取引、合計ゼロ、i64上限超過、2^40円超の警告、および貸借一致。勘定科目IDと金額を持ち、行構造を持たないため。
- **理由**: 科目名末尾の検証は科目名の文字列を必要とし、coreは `AccountId`
  しか持たないためDSL層でしか判定できない。金額表現の4ルールも表現テキストを必要とするためDSL層に留める。一方、同一勘定科目の重複は科目IDで判定するのが正（科目マスターで正規化されるためテキスト比較では誤判定する）。検証を1箇所に閉じ込めると、情報不足で判定できないルールが生じる。
- **型配置**: 違反・警告の型（`ValidationError` / `ValidationWarning`）は
  `periodless-core`
  に定義し、DSLクレートはcoreに依存して再利用する。検証の語彙（違反/警告の区分）を単一に保つため。
- **正準な桁区切り文字集合**: 桁区切り文字として妥当なのは `_`・`'`・`.`・`,`
  の4種とする。金額表現の構文仕様（DSL既存要件）は任意のASCII（空白・改行・スラッシュを除く）を桁区切り文字として受理するが、意味上妥当なのはこの4種のみであるため、検証層で判定する。
- **構文受理と検証拒否の関係**:
  金額表現ルール違反（連続区切り・非正準ASCII・基数プレフィックス）は、DSLの構文仕様上は受理される（`1,,000`・`1e3`
  などは構文としては有効）。これらは「構文上セーフだが意味上明らかに間違っている」ケースであり、構文の判定基準を変更するのではなく、検証層で拒否する。
- **0埋めの判定**: 金額表現の**数字列**が `0`
  で始まり2桁以上である場合を0埋めと判定する（`000`・`0123` は警告、`0`
  単体は警告しない）。桁区切り文字を含んでも数字列で判定するため `0,000`
  も0埋めに該当する。
- **基数プレフィックスの判定**: 表現の先頭が `0` に続けて
  `b`・`B`・`x`・`X`・`o`・`O` である場合に違反とする。`0x12345`
  は非正準ASCII（`x`）でも違反となるが、診断の明確化のため独立した違反種別として扱う。

### 3. 検証結果の表現とAPI

- **決定**:
  - `ValidationError`（enum）:
    違反の種類（省略行の位置、同一勘定科目の重複、自己取引、合計ゼロ、上限超過）。検証は全ての違反を収集し
    `ValidationErrors(Vec<ValidationError>)`（`Error` 実装）として返す。
  - `ValidationWarning`（enum）:
    警告の種類（科目名末尾が数字、合計が2^40円超）。
  - core側の-builderは
    `build() -> Result<ValidatedJournalEntry, ValidationErrors>`
    を返し、`ValidatedJournalEntry` は `journal_entry()` と `warnings()`
    を提供する。DSL側の検証器も `Result<(), ValidationErrors>` と
    `Vec<ValidationWarning>` を返す。
- **理由**:
  違反は記録を拒否し、警告は受理して通知する、という2値を一つの戻り値で表現既要（検証と構築が1パスで完結する）。警告をタプル戻り値にすると呼び出し側が読みづらく、`ValidatedJournalEntry`
  这样一个結果型で明示する方が型安全である。

### 4. hifitime の導入と Newtype 設計

- **決定**: workspace 依存へ hifitime
  を**バージョン固定**（`"=4.3.2"`）で追加する。`TransactionAt` / `CommittedAt`
  の2つのNewtypeが内部で `hifitime::Epoch`
  を保持し、外部には正規化・比較・正準文字列のみを公開する。`Epoch::now()`
  は使用しない。
- **内部表現の正規化**:
  構築時にミリ秒切り上げ正規化を適用した**正規化済み瞬間**を単一スケール（UTC生成のEpoch）で保持する。等値・順序はこの保持値に対して一貫する。
- **理由**: hifitime は浮動小数点を使わない整数固定小数点（`i16` 世紀＋`u64`
  ナノ秒）でKani形式検証済み・no_std対応であり、プロジェクトの「浮動小数点禁止・正しさ優先」原理に合致する。RFC3339のパース・フォーマットを内蔵し、Issue
  #4「入力できる」に向けた将来のDSL日時入力に直結する。Newtypeが隔離層となるため、将来の差し替えコストも低い。
- **代替案**: 自作 i64
  Newtype（依存ゼロだがRFC3339入出力を後日自作する必要）、`time`
  クレート（常规的だが精度・範囲・検証の面でhifitimeが優る）、chrono（重量で利点が薄い）。いずれもNewtypeで包む前提なら差し替え可能であり、hifitimeを採用した。

### 5. 日時の正規化アルゴリズム

- **決定**: 次の順で実装する。
  1. 入力（`Epoch` または RFC3339 文字列からパースした
     `Epoch`）をUTCの暦成分（年・月・日・時・分・秒・ナノ秒）へ分解する。
  2. `ナノ秒 % 1_000_000 > 0` なら「ミリ秒未満の端数あり」と判定し（精度保持:
     判定前に切り捨てない）、ミリ秒境界へ切り下げた値に1ミリ秒を加算する。端数なし（ミリ秒境界一致）なら値を変更しない。
  3. 正規化済み瞬間を保持し、年が 0000〜9999
     の範囲を超えていれば正規化エラー（`Result::Err`）を返す。
  4. 正準文字列
     `YYYYMMDDTHHMMSS.sssZ`（固定20バイト）は、保持するUTC暦成分から書式化する（年4桁・月日時分秒2桁・ミリ秒3桁ゼロ埋め・大文字T/Z）。
- **うるう秒（実測に基づく確定事項）**: hifitime
  4.3.2の全出力API（`to_gregorian_utc` / `to_gregorian(UTC)` / `Display` /
  `efmt` フォーマッタ / `to_rfc3339`）は秒60を**59にクランプ**し、秒60の入力は
  **59.000にエイリアス**される（正しい瞬間より1秒前）。このため:
  - 正準文字列に SS=60 は現れない（うるう秒の瞬間は表現しない）。
  - 秒60の入力は `NormalizationError::LeapSecondUnsupported`
    として拒否する（`parse_rfc3339` は入力文字列の秒フィールドを事前検証、
    `from_gregorian_utc` は `second` 引数を検証）。意図と1秒ずれた値が黙って
    記録されることを防ぐためである。
  - うるう秒挿入日の 23:59:59.999… の切り上げは翌日 00:00:00.000
    となり、この場合に限り進行量が1ミリ秒を超える（hifitimeのUTCスケール
    Epochの加算はPOSIX的で、うるう秒の境界をまたぐと1秒飛ぶため）。
- **理由**:
  暦成分からの書式化はhifitimeのフォーマッタトークン依存を避け、仕様の変換例に忠実で決定的な出力を保証する。冪等性は「境界一致なら不変」から従う。
- **代替案**: うるう秒テーブルと暦算術を自前で実装し SS=60
  を完全表現する案（スコープ大幅増・hifitime採用の意義が薄れるため不採用）。

### 6. BLAKE3 ハッシュと preimage のバイト構成

- **決定**: `blake3` クレートを使用し、`RecordHash`（`[u8; 32]`
  Newtype）を導入する。ジェネシス（前レコードなし）の前レコードハッシュは
  `[0u8; 32]` とする。preimage
  は次の決定的なバイト列（整数はビッグエンディアン固定幅、列は要素数接頭辞、可変長はバイト長接頭辞）とする:

  ```text
  b"periodless.journal-entry.v1"   // 固定ASCII接頭辞（ドメイン分離＋形式バージョン）
  || transaction_at の正準文字列    // 固定20バイト
  || committed_at の正準文字列      // 固定20バイト
  || 借方明細数: u32 BE
  || (借方明細を正規化順に) 勘定科目ID: u64 BE || 金額: i64 BE
  || 貸方明細数: u32 BE
  || (貸方明細を正規化順に) 勘定科目ID: u64 BE || 金額: i64 BE
  || 通信欄のバイト長: u32 BE || 通信欄のUTF-8バイト列（未設定なら 0）
  || 前レコードハッシュ: 32バイト
  ```

  レコードは明細列を正規化順で保持する（後述の明細順序の正規化）ため、preimageの明細列は保持順（＝正規化順）をそのまま用い、側内の明細順序の違いがハッシュに影響しない。

- **理由**:
  固定幅＋要素数＋バイト長接頭辞により、フィールド境界が一意に定まり曖昧さがない。接頭辞の
  `v1`
  は、附随情報など将来の構造追加時に形式を区別するための保険であり、構造変更時は接頭辞を上げる。
- **代替案**:
  SHA-256（慣用だが本件ではBLAKE3を指定された。速度・並列性でBLAKE3が優る）、ハッシュアルゴリズムのtrait抽象化（本時点で差し替え要件がなく、`RecordHash`
  Newtype自体が十分な隔離層となるため不採用）。

### 7. 値オブジェクト（`Amount` / `AccountId` / `Memo`）

- **決定**:
  - `Amount`: 前節のとおり（1銭単位の i64 Newtype、非負検証、checked 演算）。
  - `AccountId`: `u64` のNewtype。`account-id-encoding`
    仕様に従い、勘定区分（`id >> 60`）が `0b0001`〜`0b0110`
    であること・予約ビット（`bit 59..=48`・`bit 15..=0`）がすべてゼロであることを構築時に検証する。
  - `Memo`: 非空のUTF-8文字列のNewtype（空文字列は拒否し、未設定は
    `Option::memo` の `None` で表現）。preimageでは `None`
    をバイト長0として符号化するため、`None`
    と空の通信欄は区別されず一意に定まる。

### 8. 明細順序の正規化と取引の同一性

- **決定（DSL層）**: `JournalEntryDescription` の `PartialEq` / `Eq` / `Hash`
  は正規形に基づいて定義する。正規形は、借方明細列と貸方明細列のそれぞれを独立に、
  「金額（数値・降順）→ 勘定科目名の文字列長（降順）→
  勘定科目名の辞書順（降順）」の優先度による**安定ソート**で並べ替えた列とする。同じ行の左右の対応関係（組）は正規形に含めない。解析結果が保持する明細の並び順（入力順）は整形出力のために変更せず、等価性・ハッシュの計算のみが正規形を用いる。
- **決定（core層）**: `JournalEntry` は `build()`
  の時点で借方・貸方の各明細列を「金額（降順）→
  勘定科目ID（u64値・降順）」の安定ソートで正規化し、**正規化順で保持**する。等価性（`PartialEq`
  /
  `Eq`）とハッシュ（`Hash`）は保持順（＝正規形）に対して定義し、BLAKE3レコードハッシュのpreimageも保持順をそのまま用いる。
- **金額の数値比較（DSL層）**:
  桁区切り文字を除去し先頭ゼロを除去した数字列を金額の数値として扱い、比較は（桁数、次いで辞書順）により任意精度で厳密に行う（`i64`
  を超える桁でも正確）。ハッシュ一貫性のため、`Hash`
  は正規形の各明細について（科目名のUTF-8バイト列、正規化数字列）を投入する。
- **取引の同一性の意味**:
  借方・貸方それぞれの明細集合（科目名と金額の数値）が同一で、側内の順序のみが異なる2つの仕訳は等価（同一の取引）とみなす。同一内容の複数の取引は、取引日時・コミット日時等によって判別する（仕訳だけを見た取引の同一性）。合意済みの具体例:
  両側行の行順入れ替え・両側行の左右組み合わせ違い（組の分解）・単独行を含む順序違いは、いずれも同一の取引とみなす。
- **理由**:
  複合仕訳において側内の明細順序は意味を持たず、ソート済み列を正準形とすることで入力順に依存しない一意の等価性・ハッシュが得られる。coreが正規化順で保持することで、等価性・`Hash`・BLAKE3
  preimage
  がすべて自然に一貫し、検証（verify）は「保持する明細列が正規化順であること」を確認するだけで順序の改変も検出できる。
- **代替案**:
  入力順のまま保持し比較・ハッシュ時のみその場で正規化する案（保持内容と等価性がズレ、verifyでの順序改変検出ができないため不採用）。同じ行の左右を1つの組（ペア）として正規形に保持する案（組の分解が同一取引とみなされることが確認されたため不採用）。

### 9. 仕訳（`JournalEntry`）とフルーエントビルダー

- **決定**: `JournalEntry`
  は検証済みの仕訳内容（取引日時・コミット日時・借方明細列・貸方明細列・通信欄）とし、ハッシュは持たない。ハッシュと前レコードハッシュは台帳への追記時に確定する。構築はフルーエントビルダーで行い、`build()`
  で貸借一致・明細の妥当性・検証ルール2/3/4/6/7を検証し、明細列を正規化順（前節）へ並べ替えて保持する:

  ```rust
  use periodless_core::{
      AccountId, Amount, CommittedAt, JournalEntry, Ledger, Memo, TransactionAt,
  };

  let entry = JournalEntry::builder()
      .transacted_at(TransactionAt::parse_rfc3339("2026-11-13T02:19:00.123001Z")?)
      .committed_at(CommittedAt::parse_rfc3339("2026-11-13T02:20:00Z")?)
      .debit(
          AccountId::new(0x1000_FFFF_0001_0000)?,
          Amount::from_yen(3_500)?,
      )
      .credit(
          AccountId::new(0x5000_0000_0001_0000)?,
          Amount::from_yen(3_500)?,
      )
      .memo(Memo::new("月初の現金入金")?)
      .build()?;

  let mut ledger = Ledger::new();
  let record = ledger.append(entry)?;
  assert!(ledger.verify().is_ok());
  # Ok::<(), Box<dyn std::error::Error>>(())
  ```

  （doctest内の勘定科目IDは `docs/勘定科目一覧/accounts.yaml` の現金
  `0x1000_FFFF_0001_0000`・売上 `0x5000_0000_0001_0000` を使用する。金額は
  `from_yen` で3,500円＝350,000銭となる。）
- **追記済みレコード**: `Ledger::append` が返す追記済みレコードは `JournalEntry`
  の内容に前レコードハッシュとレコードハッシュを加えた型とし、構築は台帳経由のみ（ハッシュ値の直接設定を公開しない）。

### 10. 台帳（`Ledger`）

- **決定**:
  インメモリの追記専用コレクション。内部に追記済みレコード列を保持し、`append`
  は「コミット日時の単調性（直近と等しいか増加）・前レコードハッシュ一致（台帳側が設定）・レコードハッシュ計算」を行って追記する。`verify`
  は全レコードの preimage
  再計算と連鎖検証（最初のレコードの前ハッシュ＝32バイトゼロ、以降は直前のハッシュと一致）に加え、各レコードの借方明細列・貸方明細列が正規化順であることを確認し、改変を検出する。反復・件数参照・レコード参照のみを公開し、変更・削除のAPIは提供しない。
- **理由**:
  「過去にさかのぼって記録不可」の検証には直近レコードのコミット日時とハッシュが必要であり、台帳集約がその文脈を持つ。ハッシュ計算を台帳側に置くことで、前レコードハッシュの正当性を構築側が捏造できない。正規化順の確認により、preimageが正規化順であることに起因する「順序改変がハッシュ不一致として現れない」隙間を、正規形不变条件の違反として検出できる。

### 11. DSL側の行構造と検証器

- **決定**: `JournalEntryDescription`
  に行構造（各行の借方の明細の有無・貸方の明細の有無）を保持し、`lines()`
  相当のアクセサで公開する。DSLクレートに検証器を追加し、行構造と科目名を用いてルール1・ルール5を報告する。検証器は
  `periodless-core` の `ValidationError` / `ValidationWarning` を再利用する。
- **理由**: 行構造はDSL層にしか存在しない情報であり、coreへ持ち込むには core の
  `JournalEntry`
  が明細行表現を持つ必要性が生じる（借方列・貸方列という既存の2列表現と整合しない）。よって行構造はDSL層に留め、coreは2列表現のまま維持する。
- **行構造の表現**:
  各行を「借方の明細（任意）・貸方の明細（任意）」の組として保持し、行の並び順を保つ。

### 12. エラー型とテスト方針

- **決定**:
  各モジュールにドメインエラー型（正規化エラー・金額エラー・勘定科目IDエラー・通信欄エラー・貸借不一致・検証違反・コミット日時逆行・ハッシュチェーン不一致等）を定義し、すべて
  `Result` で返す（パニック禁止）。テストは日本語テスト関数名（例:
  `貸借が不一致の仕訳は拒否される`・`過去のコミット日時を持つ仕訳は拒否される`・`ミリ秒未満の端数は切り上げられる`・`省略行が先頭の場合は違反となる`・`側内の順序のみが異なる仕訳は同一の取引とみなされる`・`側内の順序のみが異なる仕訳は同一のハッシュになる`）で仕様のシナリオと1対1に対応させ、公開APIには
  rustdoc＋doctest を付ける。コミット前に `cargo test --workspace --all-targets`
  / `cargo test --doc` / `cargo clippy --workspace --all-targets -- -D warnings`
  / `cargo fmt --all -- --check` を通す。

### 13. クレート構成と依存

- **決定**: `crates/periodless-core/src` を
  `amount`・`account_id`・`memo`・`datetime`（`TransactionAt`/`CommittedAt`）・`record_hash`・`journal_entry`（ビルダーを含む）・`validation`・`ledger`
  のモジュールに分け、`lib.rs` から再エクスポートする。スタブ関数 `add`
  は削除する。workspace 依存に `hifitime = "=4.3.2"` と `blake3`
  を追加し、`periodless-core` から参照する。`periodless-journal-dsl` は
  `periodless-core` に依存し（検証型の再利用）、`periodless-core` は
  `periodless-journal-dsl` に依存しない。

## Risks / Trade-offs

- **[Risk] hifitime はマイナーバージョンで破壊的変更があり得る方針** →
  バージョンを厳密に固定（`=4.3.2`）し、Newtypeで内部を隠蔽する。アップグレードは独立した変更で行う。
- **[Risk] 検証が2クレートに分散し、呼び出し側が両方を使う必要がある** →
  検証型（違反・警告）を `periodless-core`
  に一元化し、警告・違反の語彙を単一にする。core側の検証（科目ID・金額）はcore、記述の検証（行構造・科目名テキスト）はDSLという情報所在地の分離は不可避である。
- **[Risk] ミリ秒切り上げ正規化によりミリ秒未満の情報は保持されない** →
  仕様上の意図（決定的な正準表現・同一境界への切り上げ許容）であり、仕様書に明記済み。異なる入力時刻が同一境界へ切り上げられても、決定性と冪等性は保証される。
- **[Risk] SS=60を含む正準文字列は一般のRFC3339パーサで読めない** →
  実測の結果、hifitime 4.3.2
  はSS=60を出力できないため、正準文字列の秒は00〜59に固定された。うるう秒の瞬間は表現せず、秒60の入力は拒否する。
- **[Risk] 合計2^40円の警告閾値が1銭単位化で変わる** →
  閾値は「2^40円」を銭単位に換算した固定値（`2^40 × 100`
  銭）として比較し、仕様の例（円表記）との対応が崩れないようにする。
- **[Risk] ハッシュ形式の将来変更（附随情報の追加等）** → preimage 接頭辞に `v1`
  を含め、構造変更時は接頭辞のバージョンを上げることで形式を区別する。
- **[Risk] preimage
  が正規化順であるため、保存済み明細の順序だけの改変はハッシュ不一致として現れない**
  →
  順序は意味を持たないため改変の影響は意味上ゼロであるが、検証（verify）が「保持する明細列が正規化順であること」を確認することで、非正規形の状態を改変として検出する。
- **[Risk] DSLとcoreで正規化のタイブレークキーが異なる（科目名文字列長・辞書順
  vs 勘定科目ID）** →
  等価性はそれぞれの層で完結しており、同一の明細集合からは同一の正規形が得られるため層間の等価性は一致する（科目名→IDの写像が関数である限り、DSL等価ならcore等価）。将来の科目マスターで別名の同一科目（エイリアス）を許す場合、DSL上は非等価でもcore上は等価になり得るが、これは同一勘定科目という意味上正しい挙動である。
